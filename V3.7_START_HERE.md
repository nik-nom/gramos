## IMPORTANT — custom domains are a proposed architectural extension, not yet deployed
The current `/v/{slug}/...` public routing supports villages by paths only. Simply adding multiple domains to Vercel **will not** map each domain to its village. Do not add client domains before implementing verified domain-to-village routing.

### Suggested commercial architecture
One Vercel Pro project + one Supabase project with strict village RLS. Store `hostname -> village_id` in a dedicated, constrained mapping table (one canonical hostname per village plus optional www alias). Verify domain ownership and Vercel DNS/SSL status before enabling. For each incoming public HTTP request:
1. normalize, validate and resolve the hostname against approved mappings; reject unknown hosts;
2. internally resolve `/` to that village's homepage and `/schemes`, `/news`, `/gallery`, `/contact` to its own public pages;
3. use the resolved village ID for data access, with RLS preventing another village's private data leakage;
4. generate canonical metadata, robots and sitemap per custom hostname (and no-index the old path and demo if duplicated);
5. keep authenticated central admin behind a separate protected URL and MFA.

Vercel automatically serves HTTPS on properly verified domains. Domains can be bought from third-party registrars and connected with DNS records.

**No customer-facing main domain is necessary**, but you need an internal admin/deployment address.

### Domain setup (AFTER domain-aware routing is implemented)
```bash
vercel link
vercel domains add shirpur.in YOUR_VERCEL_PROJECT_NAME
vercel domains inspect shirpur.in
```
At the registrar, set the DNS records shown by `vercel domains inspect`. Only mark the hostname active in GramOS once Vercel reports verification and SSL. Test all public routes and `/sitemap.xml` against each hostname.
