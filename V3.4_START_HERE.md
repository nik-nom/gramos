# GramOS v3.4 — Security, shared social links, page elements and complaint inbox

This is an **update to the existing GramOS v3.3 Node.js repository**. No new repository, Supabase project, or Vercel project is needed. Existing village `shirpur` and platform administrator are preserved.

## Install the changed files

1. Back up your current repository (or commit the current state).
2. Download `GramOS_v3.4_Changed_Files_Only.zip`.
3. Unzip it **into the root of your current repository**, where `package.json`, `index.html`, `api/`, `src/` and `vercel.json` are located. Do not add a nested GramOS folder.
4. Run:

```bash
cd ~/Downloads/gramos-shamvadi-v2
unzip -o ~/Downloads/GramOS_v3.4_Changed_Files_Only.zip -d .
npm test
npm run dev
```

Use the real path for your project if different. Open `http://localhost:8000/demo`, `http://localhost:8000/v/shirpur`, `http://localhost:8000/admin/login`.

## 1. One official social URL per village, on every page

In **Admin → Village → Village Settings**, enter Facebook, Instagram, YouTube, WhatsApp and LinkedIn URLs. Save once. The contact page and footer now read the **same** `villages.site_settings` properties, so changes appear consistently across the pages for that village. Different villages can have different official accounts. The editor validates the platform hostname (e.g. an Instagram field accepts only HTTPS `instagram.com`, not arbitrary sites); the public renderer rejects invalid links even if they were inserted directly in the database.

## 2. Add an element to a website page

In each admin page editor, click **Add element to this page**, or choose **Add elements to any page** in the sidebar. Choose the public target page and element type: plain text, heading, list, photograph, link or statistic. Enter Marathi content, optional English translation, display order and publication status. Save and publish. The element appears below that page's existing sections, before the footer. No raw HTML/JavaScript is accepted. Each village's elements are stored independently in `content_items` with `kind='page_elements'`.

## 3. Staff reviewers and the complaints inbox

Under **Supabase → Authentication → Users**, create or invite a staff account. Do not share its password. Copy the user ID (UUID). As a platform administrator, open **Admin → Village → Staff access** and add the UUID with `Complaint reviewer` permission. The staff person signs in at `/admin/login`, selects the assigned village, and opens **Visitor inbox**. They can read complaints and open private photos, but cannot change content or mark complaints resolved. Platform administrators and village editors can change complaint statuses. The inbox refreshes every 30 seconds while open, and there is a manual Refresh inbox button.

Staff membership is stored in the existing `village_members` table. RLS checks use `app_private.can_review_submissions()` for reads and `app_private.can_edit_village()` (owner/editor only) for writes. Only platform administrators can grant/remove roles. The upload bucket `visitor-uploads` remains private, with short-lived signed photo URLs for authorized members.

## 4. Configure Cloudflare Turnstile — required before accepting real forms

**Do not paste your Cloudflare secret into the chat or commit it into GitHub.** Cloudflare provides a public **site key** and a private **secret key** for each Turnstile widget. Create the widget for your actual public hostname in the Cloudflare dashboard.

- Paste **only the public site key** into `config.js`: `turnstileSiteKey: 'YOUR_PUBLIC_SITE_KEY'`.
- In **Vercel → Existing GramOS Project → Settings → Environment Variables**, set `TURNSTILE_SECRET_KEY` to the **secret key**, for Production (and Preview separately if you test there).
- Set `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and `SITE_URL` in Vercel **server-only environment variables** (never in `config.js`). `SITE_URL` must be the canonical origin, e.g. `https://village.example.in`.
- If you have authorized additional domains, set `TURNSTILE_ALLOWED_HOSTNAMES` to a comma-separated list (e.g. `village.example.in,www.village.example.in`). This restricts verification to approved hosts.
- Deploy a preview and submit a **test complaint** using the public form. Confirm that the API replies with success and that the message appears in **Admin → Visitor inbox**, then open a private photo using a reviewer account.

The backend requires Cloudflare Siteverify success, checks the verified hostname against allowed hosts, enforces input limits, rejects automated honeypot submissions, and rate-limits repeated submissions by email (3 per hour per village). A hosted WAF/rate limit is still recommended for high-volume abuse.

## 5. Deploy to your EXISTING Vercel project

```bash
npm install -g vercel
vercel login
vercel link
vercel deploy
# Test preview deployment and the form/role permissions before going live.
vercel deploy --prod
```

`vercel link` must choose the existing project. Do not create a new one. If your production site is already GitHub-connected, commit these changes and push to its production branch instead. Environment variables added or changed in Vercel normally require redeployment.
