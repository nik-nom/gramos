# GramOS v4.9 — Administration, customer register, staff logins and normal forms

Version: 4.9.0 • Compatible with the **GramOS Node.js**, two-Vercel-project layout from v4.8.1.

## What you are deploying

- **`gramos-public`**: Vercel Root Directory `apps/public`. `/` remains a 404 (no main directory), while village pages are `/v/<stored-slug>`. Active verified village domains retain `/v/<stored-slug>` in the URL.
- **`gramos-admin`**: Vercel Root Directory `apps/admin`; admin sign-in at `/admin/login`. Existing public content, village logos, Footer, images and Marathi text are retained.
- **`gramos-clean` Supabase** project `nttnrfyidokwnkqrukdb`. No new project needed.

### Existing database — live, verified

The **additive v4.9 migration is already applied** to `gramos-clean`. It added `public.village_clients`, `public.gramos_form_rate_limits`, and the guarded creation/rate-check RPCs. RLS is enabled. The existing two villages are preserved; each now has one customer-register record. The source SQL is packaged at `database/gramos_v49_client_registry_and_form_limits.sql` for auditing or another **fresh** compatible database. **Do not run it a second time against the connected production project**, and do not apply it to the older `gramos-platform` schema.

**Stored slugs matter:** one village has the slug `shirpur`; the village shown as Lohegaon has database slug **`url`**. Its existing live path is `/v/url`, not `/v/lohegaon`. Change a slug only through a controlled migration/redirect workflow after checking links and SEO.

## UI navigation

| Admin task | URL on admin project | Who can access |
|---|---|---|
| Dashboard, villages and page preview | `/admin` | Super Admin, assigned Admin and limited User |
| Register new village + customer | `/admin/new-village` | Super Admin |
| Customer register / payment / Excel or CSV | `/admin/clients` | Super Admin and assigned village Admin |
| Create village Admin or read-only User login | `/admin/staff` | Super Admin only |
| Contact details and map | `/admin/villages/<village-id>/contact` | Super Admin and assigned Admin |
| Public complaint review | Select Village → Submissions | Super Admin and authorized reviewer |

New village creation collects website slug, name, taluka and district plus contact person, email, mobile, gram sevak, Gram Panchayat, payment status and notes. The village is initially a **draft**. It is inserted transactionally with the customer record. After a successful create, the browser attempts to download the new Excel register; a permanent **Download Excel** or **Download CSV** is also available from `/admin/clients`.

**Customer register storage:** Supabase is the permanent source of truth. Each Excel/CSV export is built from current, authorized database records, so new villages appear automatically. There is no mutable Excel file stored on ephemeral Vercel disk. The sample `GramOS_Current_Customer_Register.xlsx` is only a dated snapshot, not a database replacement.

**Password privacy:** never enter passwords in the customer register, CSV, Excel, git or frontend code. Staff login uses an email as the **Login ID** and a temporary password to create a Supabase Auth account. A staff member may access only their assigned village; `User` has complaint-review access, not site editing. The Super Admin must confirm they have verified the recipient's identity and email before creating the account; send temporary passwords by a secure channel and arrange a reset.

**Contact:** village address and the safe Google Maps share or embed URL are edited in the village's Contact page. Each village has different contact values. Public Contact displays location with map link; advanced headings are collapsed by default to reduce admin clutter.

**Forms without CAPTCHA:** no Cloudflare widget/site/secret key is needed in v4.9's default settings. The public submit API validates the request, published village, allowed host, email/message lengths, honeypot, uploads and rate limits. Set `GRAMOS_FORM_CAPTCHA_ENABLED=true` **only later** if you want Turnstile, and then configure the keys/hostname allowlist. Do not set this variable to true for the keyless mode.

## Safely upload to the client's GitHub

The user's previously used local repo had diverged branches, uncommitted files and an extracted v4.8.1 ZIP subfolder; to avoid overwriting that state, use a **fresh checkout**. Download `GramOS_v4.9_Changed_Files_Only.zip` into your Mac Downloads folder and run:

```bash
cd ~/Downloads
# GitHub CLI needs to be logged into the client who owns the repo:
gh auth status
gh repo clone Sachin-022/gramos gramos-v49-deploy
cd gramos-v49-deploy

git remote -v
unzip -o ~/Downloads/GramOS_v4.9_Changed_Files_Only.zip -d .
node scripts/sync-vercel-projects.mjs
node scripts/check-vercel-projects.mjs
npm test

git status --short
# Check no .env, passwords, Vercel tokens or Supabase service-role keys are staged.
git add apps api src scripts styles.css config.js package.json tests database V4.9_DEPLOYMENT_GUIDE.md
git diff --cached --stat
git commit -m 'GramOS v4.9 village admin, register and forms'
git push origin main
```

If `gh repo clone` fails because the folder already exists, choose a NEW folder name rather than resetting a working repository. If the client account cannot authorize CLI, authenticate as the client or use repository access approved by them. In the client's Vercel Hobby account, owner-authored GitHub commits are required for private repositories; **GitHub browser login is independent of Terminal login**. Do not force-push to resolve divergence.

| Setting | `gramos-public` | `gramos-admin` |
|---|---|---|

| Framework Preset | Other | Other |

| `SUPABASE_PUBLISHABLE_KEY` | Current publishable key | Same |
| `SUPABASE_SERVICE_ROLE_KEY` | **Server-side only**, form submission | **Server-side only**, staff and domain APIs |

Add secrets in Vercel **Settings → Environment Variables**, never in `config.js`, GitHub or screenshots. The `config.js` file holds only the public Supabase URL/publishable key. After adding keys, redeploy BOTH projects and check they built the new git commit.

## Smoke checks on Vercel after deployment

1. `https://gramos-public.vercel.app/` → 404, no main landing page.
2. `https://gramos-public.vercel.app/v/shirpur` and `/v/url` → correct **published** village websites unless an active verified custom-domain redirect applies; correct villages only.
3. `https://gramos-admin.vercel.app/admin/login` → login. Sign in with an **existing Supabase Auth** account that has Super Admin or assigned-village permissions.
4. At `/admin/clients`, inspect both existing records (unknown payment remains **Not recorded**); edit one and refresh, verify the value persists. Export both CSV and XLSX, inspect files, verify no passwords.
5. At `/admin/new-village`, use a TEST village slug and **correct customer details**, confirm it creates a DRAFT and is added to register and export. Unpublish/archive test village afterwards rather than deleting production data.
6. At `/admin/staff`, as Super Admin, verify recipient identity and create a test Admin for the correct village and separately a User; test both in private browser sessions. Ordinary admins must be denied account creation. Never share a user password in screenshots.
7. Visit the appropriate village Contact page, confirm the formal address/map link and iframe. Publish contact changes, and verify no other village changes.
8. Submit a normal visitor test form **without CAPTCHA** and confirm it reaches the village's admin Submissions inbox; ensure wrong-domain, wrong-village and spam/rate-limit requests are rejected.
9. If using domains, verify the real DNS and Vercel ownership status before activation and check each village's `/v/<slug>` and hostname-specific `sitemap.xml`. Custom domain configuration is not automatically completed by deploying v4.9.
10. Check desktop, phone, Marathi and English versions, image uploads, page preview, draft/publish/unpublish, role security and no text/card overflow.

## Rollback

Revert the deployment commit in GitHub and redeploy both Vercel projects to the last known good commit. **Do not drop** `village_clients`, `gramos_form_rate_limits` or other Supabase tables during an emergency rollback. The old website can continue using the same village and auth data. Backup database before major production changes.
